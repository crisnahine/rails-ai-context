# The Claude Code plugin runs the installed gem through ruby

Status: accepted

The repository is a Claude Code plugin marketplace with one plugin, `plugins/rails-ai-context`. A plugin is a folder Claude Code copies and starts commands from; it cannot run Bundler or install a gem, and its `.mcp.json` and hooks are one command line for every platform.

## Decision

- The plugin ships no copy of the gem. Its server entry is `ruby ${CLAUDE_PLUGIN_ROOT}/scripts/serve.rb`, and the script loads the installed gem's own binary with `serve`, as its RubyGems binstub would. The binary then does what a standalone install does: finds the app root from the folder Claude Code started in, and hands off to the app's bundled copy when the Gemfile has one. When it cannot start, the script exits 1 and says why on stderr: no gem for that Ruby (naming `gem install rails-ai-context`), a Ruby older than 3.1, or the installed gem's own activation error.
- The server is started as `ruby` with arguments: `ruby` is an executable on every platform, while a gem's binstub is a batch file on Windows, which a client that starts servers without a shell cannot run. One plugin file has no way to say "only on Windows". The hook is the shell form `ruby "${CLAUDE_PLUGIN_ROOT}/scripts/session_start.rb"`: Claude Code substitutes the path before any shell sees it, the quotes hold its spaces, and a Claude Code too old for the exec form still runs it.
- The plugin has no `version`. Claude Code then versions it by commit, so a fix reaches users without a manifest bump that the release checklist would have to carry. What the server does is versioned by the gem it runs.
- The six rules the context files open with come from a SessionStart hook on startup, clear and compact (a resumed session holds them already), since the plugin writes no context file. The hook asks the installed gem's `CLI::AppRoot` for the app, so it speaks exactly where the server serves one. It prints `rules.md` unless the app's `CLAUDE.md` or `.claude/rules/rails-mcp-tools.md` carries the generator's rules (an app found below the start folder does not count, since Claude Code reads that `CLAUDE.md` only later), or `.rails-ai-context.yml` or an initializer turns them off (a literal assignment; the hook runs no app code). It prints nothing where the server would refuse the root (no app source, as `EntryBoot.app_present?` judges), without the gem, or with one older than `AppRoot` (5.33.0): there are no tools for the rules to name. In a folder of several apps the server script says to start Claude Code in one of them, since the binary's own advice, `--app-path`, is not something a plugin entry can pass. `rules.md` is `ToolGuideHelper`'s rendering word for word, and a spec holds it there, checks every tool it names against the server's, and runs the hook against this checkout's `AppRoot`, so a rename there fails here.
- `ClaudeCodeSettings` is the one place that knows Claude Code's files, and it reads them per session, by the folder the session started in, as Claude Code does. A session reads that folder's project settings, the local settings of its git root and of the folder, the user's and managed settings (with their drop-ins, merged per plugin key); every `.mcp.json` from that folder up to the filesystem root, whose servers start in that folder; and the `/mcp` toggles and local servers `.claude.json` keeps under the folder's git root. `.claude.json` moves with `CLAUDE_CONFIG_DIR`. Managed settings come from the managed file and its drop-ins, not from an MDM profile or the Windows registry.
- The sessions that matter are those started where the plugin would serve this app, as `AppRoot` and `EntryBoot` judge: the app, a folder inside it, a folder above that holds it alone, and any folder `.claude.json` keeps a project for. The plugin runs in one where it is enabled (`true` or a list of version constraints), installed (a machine with no install registry has installed nothing), and not turned off in `/mcp`.
- `doctor` judges the session started where the app's config lives. If the plugin runs there, Claude Code's MCP check passes without a `.mcp.json`, with no AI tools chosen the check stops there, and the activation check runs as for any installed binary. If it runs only in another session, `doctor` names that folder and how to turn it on here: `/mcp` where it was turned off, else `claude plugin enable ... --scope local`. Enabled but not installed, it asks for the install, naming the marketplace, since the install generator's fix would add the second server.
- A server of the gem's, under any name and in any command form, that a session running the plugin would also start is a warning naming the command that removes it and the folder to run it in, since Claude Code matches duplicates by command and these never match the plugin's. An entry naming no app counts, since it starts in the session's folder, which resolves to this app; one naming another app, or an app path `doctor` cannot read, does not, so no fix removes another app's server.

## Consequences

The plugin ships from `main` on every commit, not from a release tag. It must keep working with released gems: it may only use what a released gem already has. The server name `rails-ai-context` and the script paths are what users' Claude Code configs and permission rules hold on to; renaming either breaks them. The plugin serves one app per session, the one `AppRoot` resolves from where Claude Code started; a folder of several apps still needs the workspace entries `init` writes.

## Alternatives not taken

- **`rails-ai-context serve` as the command**: what the standalone generator writes, but it does not start on Windows.
- **A shell launcher that picks `bundle exec` or the bare binary**: needs a shell on Windows too, and repeats the handoff the binary already makes.
- **The rules in the server's MCP instructions**: every client would get them, including apps whose `CLAUDE.md` already carries them, so they would load twice there.
- **The rules as a skill**: loaded only when the model chooses to, and in a real edit session it went unused. The context files put the rules in every session, and the hook does the same.
- **The hook finding the app itself**: a second copy of `AppRoot`'s rules (home folders, dependency folders, symlinks, nested apps) that drifted from it in its first version.
