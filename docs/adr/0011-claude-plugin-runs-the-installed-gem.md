# The Claude Code plugin runs the installed gem through ruby

Status: accepted

The repository is a Claude Code plugin marketplace with one plugin, `plugins/rails-ai-context`. A plugin is a folder Claude Code copies and starts commands from; it cannot run Bundler or install a gem, and its `.mcp.json` and hooks are one command line for every platform.

## Decision

- The plugin ships no copy of the gem. Its server entry is `ruby -e "load File.join(ENV.fetch('CLAUDE_PLUGIN_ROOT'), 'scripts', 'serve.rb')"`, a command line no plugin update changes, so one `allowedMcpServers` entry admits it for good (and admits any plugin that ships the same line), and the script loads the installed gem's own binary with `serve`, as its RubyGems binstub would, at the version `scripts/gem_requirement.rb` names. The binary then does what a standalone install does: finds the app root from the folder Claude Code started in, and hands off to the app's bundled copy when the Gemfile has one. Where it cannot serve, the script says why on stderr in one line, naming the Ruby and the folder it ran in: no gem for that Ruby (naming `gem install rails-ai-context`), only an older one (naming `gem update`), a Ruby older than 3.1, a bundle Claude Code inherited from `bundle exec` that lacks the gem, the installed gem's own activation error or load failure, and, on a gem older than 5.38.0, several apps or none. It then answers the MCP handshake itself, with no tools and that line as the server's instructions, rather than exiting: Claude Code 2.1.308 skips a plugin server that failed to start in every new session for 15 minutes, keyed by its command line, which is the same in every folder, so one session outside a Rails app would turn the plugin off everywhere. From 5.38.0 the script sets `RAILS_AI_CONTEXT_PLUGIN=1` before it loads the binary, and the gem's `serve` refuses the same way (`CLI::Refusal`) wherever it would have printed an error and exited: no app source, a static tier that cannot read the app, an error the command raised. Claude Code 2.1.310 asks `server/discover` first; the refusal answers it with method-not-found, after which a client sends `initialize`, the one handshake that carries the instructions on every protocol. Where the serve hands the app to its bundled copy, the plugin's process stays in front of that copy as a proxy (ADR-0012), so a copy older than 5.38.0 that exits still leaves a connected server that names why. A start that fails before the script runs still exits, and gets that skip.
- The server is started as `ruby` with arguments: `ruby` is an executable on every platform, while a gem's binstub is a batch file on Windows, which a client that starts servers without a shell cannot run. One plugin file has no way to say "only on Windows". `-e` names no script, so rbenv picks the Ruby by the session's folder, not the plugin's. The hook is the shell form `ruby -- "${CLAUDE_PLUGIN_ROOT}/scripts/session_start.rb"; exit 0`: Claude Code substitutes the path before any shell sees it, the quotes hold its spaces, a Claude Code too old for the exec form still runs it, and `exit 0` keeps a folder where `ruby` cannot start, or a Ruby too old to read the script, from showing a hook error at every session start. The `--` ends rbenv's search of ruby's arguments for a script, whose folder (the plugin's) would otherwise pick the Ruby in place of the session's folder; ruby reads it as the end of its options everywhere.
- The plugin has no `version`. Claude Code then versions it by commit, so a fix reaches users without a manifest bump that the release checklist would have to carry. What the server does is versioned by the gem it runs.
- The gem requirement is the first release with everything both scripts call and every tool and parameter `rules.md` names. The plugin ships from `main` to users who may have only that release, so CI installs it from RubyGems and runs the scripts against it, and fails while RubyGems lacks it. A release that changes what the plugin relies on (a named tool or parameter, what `doctor` or the update notice says about the plugin) raises the requirement to itself in a commit after it is published, and a rename keeps the old name working, and in the rules, until that commit.
- The six rules the context files open with come from a SessionStart hook on startup, clear and compact (a resumed session holds them already), since the plugin writes no context file. The hook activates the installed gem as the server does and asks its `CLI::AppRoot` for the app, so it speaks exactly where the server serves one, and prints nothing where the server would refuse the root (no app source, as `EntryBoot.app_present?` judges), without a gem that meets the requirement, or where the app's bundled copy, which the server hands the app to, is older than it. It prints `rules.md` unless Claude Code already loads the generator's rules for that session: the app's `CLAUDE.md` or `.claude/rules/rails-mcp-tools.md`, or its `AGENTS.md` where `CLAUDE.md` imports it or no `CLAUDE.md`, `.claude/CLAUDE.md` or `CLAUDE.local.md` is on the way up from the start folder to just below the filesystem root, or one of those files on the way up that carries them (an engine's above its test/dummy app), the user's own memory left out (Claude Code's default Project instructions). An app found below the start folder does not count, since Claude Code reads its files only later. Nor does it print where the app turns the rules off: `.rails-ai-context.yml`, aliases included, or a configure block in `config/application.rb`, the environment's file or an initializer setting `anti_hallucination_rules` to `false` or `nil`, the last such literal in load order winning over the file. The hook runs no app code, so only a literal that ends its statement counts, outside `=begin` blocks. Rule 3 leaves out the `rails_get_config` sections `skip_tools` turns off, from the YAML or a literal list, assigned or appended, as the generator writes it. `rules.md` is `ToolGuideHelper`'s default rendering word for word, and a spec holds it there, checks every tool and parameter it names against the server's, and runs the hook against this checkout's `AppRoot`, so a rename there fails here. In a folder of several apps the server is ADR-0012's router, and the hook prints the rules with a last line naming the apps and the `app` argument a call picks one by; on a gem older than 5.38.0 the server script says to start Claude Code in one of them, by their paths from there, and the hook's last line names the `rails-ai-context --app-path <app> tool <name>` form, since `--app-path` is not something a plugin entry can pass. The hook finds the user's own memory in the config folder `ClaudeCodeSettings.user_config_dir` names.
- `ClaudeCodeSettings` is the one place that knows Claude Code's files, and it reads them per session, by the folder the session started in, as Claude Code 2.1.308 does. A session reads that folder's project settings, its own local settings and then its git root's, which win (on macOS and Linux, where the root is not the home folder, the repository is not bare, and the root, its `.git` and its `.claude` belong to the user; otherwise only the folder's own), the user's and managed settings (with their drop-ins), merged per plugin key; every `.mcp.json` from that folder up to the filesystem root, whose servers start in that folder; and the `/mcp` toggles and local servers `.claude.json` keeps under the folder's git root. A linked worktree's git root is its repository: the main checkout, or a bare repository's own folder. Only `true` turns a plugin on. A user, project or local settings file whose `enabledPlugins` fails Claude Code's schema is dropped whole; a managed one loses only the entries that fail, and a managed file that is not a JSON object stops Claude Code from starting. Only `enabledPlugins`' shape is checked, though Claude Code drops a file for other schema errors too. `.claude.json` moves with `CLAUDE_CONFIG_DIR`, and an older `.config.json` in the config folder is read in its place where one is left. A `CLAUDE_CONFIG_DIR` in the `env` block of the managed settings, else of the user's, moves `settings.json` and `plugins/` once more but not `.claude.json`; a relative one, empty included, leaves each session reading its own folder's. Managed settings come from the managed file and its drop-ins, read as if all were in force, not from the Claude console's server-managed settings, an MDM profile or the Windows registry. The MCP policy keys keep a server from starting: a deployed `managed-mcp.json`, which starts its own servers alone, a `deniedMcpServers` entry by name, exact command or url pattern, an allowlist that admits it by none of those (a plugin's server only by its exact command, since its name holds colons an allowlist entry cannot), and the managed lock on user and project servers, which fails closed as Claude Code's does. The managed marketplace policy (`strictKnownMarketplaces`, `blockedMarketplaces`) keeps a plugin from loading; an entry form the gem does not know counts as no evidence.
- The sessions that matter are those started where the plugin would serve this app, as `AppRoot` and `EntryBoot` judge: the app, the two folders above it, the folder `doctor` runs in, and any folder `.claude.json` keeps a project for. The plugin runs in one where it is enabled, installed for that session's project (a project or local install counts in its own project only, a plugin from a marketplace added by a local folder or file needs no install but needs that folder, and where Claude Code never ran, as on CI, there is nothing to install), not turned off in `/mcp` and not blocked by policy.
- `doctor` judges the session started where the app's config lives, and checks Claude Code wherever the plugin is chosen, whatever AI tools were chosen and under CLI-only mode. Where Claude Code never ran, as on CI, what the plugin needs from the machine is a warning, so a STRICT run stays green. If the plugin runs there, Claude Code's MCP check passes without a `.mcp.json`, and with no AI tools chosen another tool's config counts only where it exists and is broken. If it runs only in another session, `doctor` names that folder, how to turn it on here, and any second servers there. Where `managed-mcp.json` is deployed, `doctor` judges Claude Code by it alone, by the server of the gem's it names for this app, what keeps that one off (a deny or `/mcp`), and whether it can start, as a `.mcp.json` entry is judged. If the plugin runs nowhere, `doctor` names why, in this order: a `CLAUDE_CONFIG_DIR` that is empty or relative, wherever it is set, a managed settings file Claude Code cannot read, not installed (asking for an install at the scope that leaves a committed file alone, and with no source where Claude Code knows the marketplace), a local marketplace folder that is gone, blocked by the marketplace policy, blocked by the MCP policy (naming every deny entry that holds it off, or the allowlist entry that admits it without turning the others to matching by command), or its server turned off in `/mcp`. Where the app's committed settings turn the plugin on and local or managed settings turn it off for this user, it names the file that does. It never names `init` for Claude Code's `.mcp.json` where the committed settings turn the plugin on, since the install leaves that file alone there and `init` would change nothing. Existing context files are still checked for staleness; only their absence passes.
- A server of the gem's, under any name and in any command form, or an HTTP entry under its name, that a session running the plugin would also start is a warning naming the commands that remove it and the folders to run them in, since Claude Code matches duplicates by command and these never match the plugin's. An entry naming no app counts, since it starts in the session's folder, which resolves to this app, and so does one whose app path is `${CLAUDE_PROJECT_DIR:-...}` or `${PWD}`, which Claude Code expands from its own environment; one naming another app, or an app path `doctor` cannot read, does not, so no fix removes another app's server. A `.mcp.json` entry is removed where the committed settings turn the plugin on, and turned off with `/mcp` where only one user's do, since the file is then the team's. Turning the plugin off is offered too only where it leaves each session one server: once per repository, for every id the plugin runs under, and never where managed settings turn it on.
- The install generator and `init` write no Claude Code server into `.mcp.json` where the app's committed settings turn the plugin on, and say why; so does `init` in a folder holding one app whose own committed settings turn it on, since the plugin serves that app from there; it still writes the app's own `.mcp.json` for sessions started in the app, which do not read that folder's settings, and says so. In a folder of several apps whose own committed settings turn the plugin on it writes no Claude Code server either, since the plugin serves each app there (ADR-0012). Whether the committed plugin runs for this user is one `ClaudeCodeSettings#serving` verdict, which `init` and `doctor` both render. `uninstall` names, before it suggests removing the gem the plugin runs, `claude plugin disable <id> --scope local` once per repository whose sessions run the plugin, run in a session folder that enables it, and the uninstall of the one install that serves them, by that install's own scope and folder.

## Consequences

The plugin ships from `main` on every commit, not from a release tag. It must keep working with the release its requirement names, which CI checks; a release that changes what the plugin relies on raises the requirement only once it is published. The server name `rails-ai-context` and the script paths are what users' Claude Code configs and permission rules hold on to; renaming either breaks them. The plugin serves the session target `AppRoot.target` gives for where Claude Code started: one app, or each app of a folder of several through ADR-0012's router. `ClaudeCodeSettings` models what Claude Code 2.1.308 does where its docs are silent, so a Claude Code release that changes it can make `doctor`'s verdicts wrong until the model follows.

## Alternatives not taken

- **`rails-ai-context serve` as the command**: what the standalone generator writes, but it does not start on Windows.
- **A shell launcher that picks `bundle exec` or the bare binary**: needs a shell on Windows too, and repeats the handoff the binary already makes.
- **The rules in the server's MCP instructions**: every client would get them, including apps whose `CLAUDE.md` already carries them, so they would load twice there.
- **The rules as a skill**: loaded only when the model chooses to, and in a real edit session it went unused. The context files put the rules in every session, and the hook does the same.
- **The hook rendering the rules from the installed gem**: matches any version's wording, but loads the whole gem at every session start, about a second more, for what a version requirement already keeps in step.
- **The hook finding the app itself**: a second copy of `AppRoot`'s rules (home folders, dependency folders, symlinks, nested apps) that drifted from it in its first version.
- **The hook booting the app to read its settings**: exact, but slow and able to run app code at every session start, for a switch nearly every app sets as a literal.
